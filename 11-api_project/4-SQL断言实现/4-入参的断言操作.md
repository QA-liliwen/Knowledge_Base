
## 七、parse_sql_assert_expr：拆断言表达式

```py
# 解析断言表达式部分:
# 常规三方校验 "=/data/answer='c'" -> =, /data/answer, 'c'
# 带前导操作符 "=/rows/0/status=1" / ">=/row_count>=2" -> 前导操作符为比较操作符
# 省略预期值 "=/questions/0/solution" -> 预期返回 None，语义为查库值与入参值直接比对
def parse_sql_assert_expr(assert_expr):
    expr = assert_expr.strip()  # 去首尾空白
    # 拆断言表达式开头的那个操作符（ASSERT_EXPR_PATTERN 已内联，不再设模块常量）
    match = re.compile(r'^(==|!=|>=|<=|=|>|<)\s*(/.*)$', re.S).match(expr)
    if match:
        op = match.group(1)
        rest = match.group(2).strip()
        # 在剩余部分里找第一个操作符，切出「路径」和「预期值」（OP_ORDER 已内联为元组字面量）
        for o in ('==', '!=', '>=', '<=', '=', '>', '<'):
            if o in rest:
                path, expected = rest.split(o, 1)
                # 返回路径、操作符、预期值
                return path.strip(), op, expected.strip()
        # 没有预期值，则置 None
        return rest, op, None
    raise AssertionError(f"SQL断言格式错误（未找到运算符）: {assert_expr}")
```

**解释**：四种输入形态——

| 输入                       | 输出 (path, op, expected)                | 用途             |
| ------------------------ | -------------------------------------- | -------------- |
| `=/data/answer='c'`      | `('/data/answer', '=', "'c'")`         | 三方校验           |
| `=/questions/0/solution` | `('/questions/0/solution', '=', None)` | 两方校验（None 是信号） |

**关键点**：为什么不能复用引擎的普通 parse_expr——`"SQL"=/data/answer='c'` 紧贴 SQL 的 `=` 只是分界符，直接按 `=` 切会把 SQL 尾巴切进路径。所以先用正则把前导操作符「吃掉」，再在剩余部分里找预期值分隔符。原「四种输入形态」中的 `>=/row_count>=2`（行数断言）属于已删除的形式2，不再支持。


## 八、extract_db_value：查库取值

```py
# 落库校验形式：从查询结果取比较值，字段名 = 入参路径最后一段
# 字段不存在时：仅一列则取唯一列，多列则报错（可用 as 别名与入参字段对齐）
def extract_db_value(result, req_path):
    rows = result['rows']
    if not rows:
        raise AssertionError(f"SQL查询结果为空，无法比较字段: {req_path}")
    column = req_path.strip('/').split('/')[-1]
    row0 = rows[0]
    if column in row0:
        return row0[column]
    if len(row0) == 1:
        return next(iter(row0.values()))
    raise AssertionError(f"查询结果不存在字段 {column}（可用 as 别名与入参字段对齐，或只查询该列）")
```

**解释**（`/data/answer` + 查询结果 `{"rows": [{"answer": "c"}]}` 走一遍）：
1. 空结果先报错（WHERE 条件没查到行 = 落库没发生，本身就该 failed）
2. column=`answer`（路径末段），第 1 行有 answer 列 → 取 `"c"`
3. 列名对不上时：只查了一列就取那列（写 SQL 的人意图明显）；多列才报错，提示用 as 别名

**关键点**：列名=路径末段的假设依据——API 入参字段名与表列名通常一致（落库直传）；不一致场景用 as 别名对齐（`select content as answer from ...`）。

## 九、smart_equal：JSON 归一化比较
```py
# 归一化比较：数据库常以字符串存 JSON（如 {"ids":["D"]}），入参是结构化对象
# 双方先直接比较；任一侧能解析成 JSON 的一律按解析后的结构深度比较
def smart_equal(actual, expected):
    if actual == expected:
        return True

    def _as_json(v):
        if isinstance(v, (dict, list)):
            return v
        if isinstance(v, str):
            try:
                return json.loads(v)
            except (json.JSONDecodeError, ValueError):
                return None
        return None

    a = _as_json(actual)
    e = _as_json(expected)
    if a is not None and e is not None:
        return a == e
    return False
```

**解释**：解决「入库 JSON 字符串 vs 入参结构化对象」的等值问题。传 `{"solution": {"ids": ["D"]}}`，库列存 `'{"ids": ["D"]}'`——直接 == 是 str vs dict 必然 False。比较顺序：
1. 先直接 ==（标量、同类型一步到位）
2. 双方各自尝试转 JSON（dict/list 原样；字符串 json.loads；失败返回 None）
3. 双方都转成 → 深度比较；否则 False

**关键点**：
- 库里 `'{ "ids" : [ "D" ] }'` 与入参 `{"ids": ["D"]}` 空格/键序差异在解析后消失
- 一侧非 JSON 字符串（`'abc'`）一侧 dict → False，不误判
- 只在 `=`/`==` 时被引擎叠加使用（sql_op），`>=` 等数值比较保持原生语义

## 附：一条断言经过本模块的数据形态变化

| ③④ 判定 | 库名有、四要素齐 | 不跳过，继续 |
