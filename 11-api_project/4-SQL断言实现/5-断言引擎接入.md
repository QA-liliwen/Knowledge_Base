# run_request.py

> 按**运行时逻辑进入的顺序**组织：从 pytest 启动开始，跟着一条 `set:` 和一条 `sql:` 断言走完全流程。
> 文件物理顺序（导入区处理器函数run_mainpytest 入口）与执行顺序不同，本文按执行顺序阅读代码。

## 执行顺序总览

```
pytest 启动
  pytest_generate_tests（收集钩子） test_api 按 cases 文件展开成 N 条
      test_api(case)  run_main(case)
          状态码断言 + resp_json = resp.json()
          variables = {}（每条用例独立变量池）
          for assertion_str in case['assertions']:（按书写顺序逐条）
              partition(':') 拆前缀
              分支 set:  assert_set
              分支 sql:  assert_sql
                  run_sql_assertion（执行器：解析跳过判定替换执行）
                  parse_sql_assert_expr（拆路径/操作符/预期值）
                  convert_expected（预期值两层解析）
                  入参分支：extract_by_path  extract_db_value
                       预期值=None  两方校验
                       预期值存在  三方校验（先入参后查库）
              其他前缀走老分发（len/exists/type/header/in/无前缀）
全部用例结束  conftest.py 的 pytest_terminal_summary 回调平台
```

##  一、pytest_generate_tests：收集阶段（还没发任何请求）

```py
def pytest_generate_tests(metafunc):
    cases_file = metafunc.config.getoption("--cases-file") or os.environ.get("CASES_FILE")
    if not cases_file:
        return
    with open(cases_file, "r", encoding="utf-8") as f:
        cases_data = json.load(f)

    metafunc.parametrize(
        "case",
        cases_data,
        ids=[c['CaseID'] for c in cases_data]
    )
```

**解释**：pytest 的收集钩子（框架按函数名回调，业务代码从不调用它）。读 cases JSON 文件（executor 落盘的 `{run_id}_cases.txt`），把唯一的测试函数 `test_api` 参数化成 N 条用例。每条用例的 case 参数就是 cases 列表里的一个完整 dict（含 body、assertions、sql_database）。

**关键点**：
- 只在收集阶段跑一次，不在每条用例执行时重复读文件
- `ids` 让报告里显示 `test_api[case_001]` 而不是 `test_api[case0]`，与平台用例编号对齐
- 环境变量 CASES_FILE 是兜底入口，正常链路走 --cases-file 命令行参数

```py

```

**解释**：参数化后每条用例调用一次。真正的逻辑全在 run_main 里。

##  请求与状态码断言

```py
def run_main(case):
    if case.get('is_active') != 'Y':
        pytest.skip(f"用例 {case['CaseID']} 未启用")

    resp = run_request(url=case['url'], method=case['method'], headers=case['headers'], body=case.get('body', ''))
    log.info(f"状态码断言: 实际={resp.status_code}, 期望={case['expected_status_code']}")
    assert resp.status_code == case['expected_status_code'], f"状态码: 实际={resp.status_code}, 期望={case['expected_status_code']}"
    resp_json = resp.json()
```

**解释**：先判启用（SKIPPED 不算失败） 发请求  状态码硬断言（失败即本条用例终止，后面的数据断言不执行） 响应体解析成 dict。`resp_json` 是后续所有 JSONPath 断言和 `set:` 变量提取的数据源。

##  断言循环与前缀拆分

```py
    for assertion_str in case['assertions']:
        ASSERT_HANDLERS = {
            'len': assert_len,
            'exists': assert_exists,
            'type': assert_type,
            'header': assert_header,
            'in': assert_in,
        }
        # 分离断言的前缀和冒号和剩余内容，
        prefix, sep, rest = assertion_str.partition(':')
```

**解释**：断言列表按书写顺序逐条执行（`;` 分隔符在 executor 组装时已拆成列表）。`partition(':')` 只切**第一个**冒号，切出三元组：

| assertion_str | prefix | sep | rest |
| --- | --- | --- | --- |
| `set:qid=/question_id` | `set` | `:` | `qid=/question_id` |
| `sql:select ...=/data/answer='c'` | `sql` | `:` | SQL 里再有冒号也不影响（只切第一个） |
| `/data/status=1` | 整串 | `''` | `''` |

**关键点**：`sep` 为空串 = 没冒号 = 无前缀断言，后面所有 `if sep and ...` 分支自然全部跳过，落到默认解析一行拆分同时完成类型识别和兜底。

##  二、分支 set:  assert_set

```py
        if sep and prefix == 'set':

```

进入 assert_set 函数体：

```py
def assert_set(expr, variables, resp, resp_json):
    name, sep, path = expr.partition('=')
    if not sep or not name.strip() or not path.strip():
        raise AssertionError(f"变量提取格式错误（正确格式 set:变量名=JSON路径）: set:{expr}")
    name = name.strip()
    try:
        value = extract_by_path(resp_json, path.strip())
    except (KeyError, IndexError, TypeError):
        log.error(f"变量提取失败: {name} <- {path.strip()}（路径不存在）")
        raise AssertionError(f"变量提取失败: {name} <- {path.strip()}（路径不存在）")
    variables[name] = value
    log.debug(f"变量提取: {name} = {value}")
```

**解释**（`set:qid=/question_id` 走一遍）：
1. `partition('=')` 再切一次  name=`qid`，path=`/question_id`
2. `extract_by_path(resp_json, '/question_id')` 从**响应**取值 123
3. `variables['qid'] = 123` 写入第步建的变量池
4. continue 回到循环，处理下一条断言

**关键点**：
- 提取点就报「路径不存在」而不是留到 sql: 报「变量未定义」，定位更准
- `set:` 必须写在引用它的 `sql:` 之前循环按书写顺序执行，先提取后引用

##  三、分支 sql:  assert_sql 入口

```py
        if sep and prefix == 'sql':
            assert_sql(rest, case.get('sql_database', ''), variables, case.get('body'))
            continue
```

**解释**：rest 是 `select ... where id=${qid}=/data/answer='c'` 整段。四个入参：
- `rest`：断言内容
- `case.get('sql_database', '')`：测试项配的库名（get 兜底，旧用例没这个 key 不报错，走跳过）
- `variables`：第步的变量池（含刚 set: 的 qid）
- `case.get('body')`：入参 dict，三方/两方校验的数据源

进入 assert_sql 函数体（形式2「查询结果直比」已删除，只保留落库校验一种形式）：

```py
# SQL 断言（落库校验）:
# 三方校验: sql:select answer from t where id=${qid}=/data/answer='c'
#   查库值、入参值 都与手输预期值比较
# 省略预期值: sql:select solution from t where id=${qid}=/questions/0/solution
#   两方校验：查库值 == 入参值（库内存 JSON 字符串时自动解析后深度比较）
# 库名为空或连接四要素缺失时跳过（不报错），其余异常往上抛
def assert_sql(expr, sql_database, variables, body=None):
    # 传入的 断言内容， sql库， 变量池后，返回 断言表达式, 查询结果
    parsed = run_sql_assertion(expr, sql_database, variables)
    if parsed is None:
        return
    assert_expr, result = parsed
    # 解析断言表达式部分: =/data/answer='c' -> =, /data/answer, 'c'
    path, op, expected = parse_sql_assert_expr(assert_expr)
    expected = convert_expected(expected) if expected is not None else None
```

##  run_sql_assertion：交给执行器（sql_assert.py）

```py
def run_sql_assertion(expr, sql_database, variables):
    sql, assert_expr = parse_sql_assertion(expr)          # 拆成 (SQL语句, 断言表达式)
    if not sql_database:                                  # 测试项没配库名  跳过
        log.info(f"SQL断言跳过（测试项未配置SQL库名）: {sql[:100]}")
        return None
    if not get_conn_config():                             # 环境没配连接（如生产） 跳过
        log.info(f"SQL断言跳过（当前环境未配置SQL连接）: {sql[:100]}")
        return None
    sql = replace_vars(sql, variables)                    # ${qid}  123
    try:
        result = execute_sql(sql, sql_database)           # pymysql 执行  {"rows":[],"row_count":N}
    except AssertionError:
        raise
    except Exception as e:
        raise AssertionError(f"SQL执行失败: {e}")
    return assert_expr, result
```

**解释**（本例走一遍）：
1. `parse_sql_assertion`：按「操作符紧跟/」分界  sql=`select answer from t where id=${qid}`，assert_expr=`=/data/answer='c'`
2. 两个跳过判定：库名空 / 四要素缺失  返回 None  处 `parsed is None` 直接 return，用例继续跑其余断言（配置缺失是正常降级不是错误）
3. `replace_vars`：`${qid}` 从变量池取 123 替换，变量未定义会在这里报错
4. `execute_sql`：安全校验（SELECT/WITH 开头、禁分号） pymysql 查询  包装 `{"rows": [{"answer": "c"}], "row_count": 1}`
5. 返回 `(assert_expr, result)` 给 

##  parse_sql_assert_expr：拆断言表达式

```py
    path, op, expected = parse_sql_assert_expr(assert_expr)
```

执行器内：

```py
def parse_sql_assert_expr(assert_expr):
    expr = assert_expr.strip()
    # 拆断言表达式开头的那个操作符（ASSERT_EXPR_PATTERN 已内联，不再设模块常量）
    match = re.compile(r'^(==|!=|>=|<=|=|>|<)\s*(/.*)$', re.S).match(expr)
    if match:
        op = match.group(1)                      # '='
        rest = match.group(2).strip()            # '/data/answer='c''
        # 在剩余部分里找第一个操作符，切出「路径」和「预期值」（OP_ORDER 已内联为元组字面量）
        for o in ('==', '!=', '>=', '<=', '=', '>', '<'):
            if o in rest:
                path, expected = rest.split(o, 1)  # '/data/answer' + "'c'"
                return path.strip(), op, expected.strip()
        return rest, op, None                    # 省略预期值  None 信号
    raise AssertionError(f"SQL断言格式错误（未找到运算符）: {assert_expr}")
```

**解释**：`=/data/answer='c'`  `('/data/answer', '=', "'c'")`。为什么先吃前导操作符再找预期值分隔符SQL 紧贴的 `=` 只是分界，直接按 `=` 切会把 SQL 尾巴切进路径。

##  convert_expected：预期值两层解析

```py
    expected = convert_expected(expected) if expected is not None else None
```

**解释**：复用现有断言的预期值解析：`'c'` 剥引号成 `c`，`123` 转 int，`{"a":1}` 转 dict。

**关键点**：条件必须是 `is not None` 而不是 `if expected`convert_expected 可能返回合法假值（0、False、空串），且 None 本身是「省略预期值」的信号，不能丢。

##  入参分支：先拿两个值

```py
    if not isinstance(body, (dict, list)):
        raise AssertionError(f"入参不是JSON对象，无法按入参路径断言: {path}")
    column = path.strip('/').split('/')[-1]
    try:
        req_value = extract_by_path(body, path)       # 入参值：从请求 body 取
    except (KeyError, IndexError, TypeError):
        log.error(f"入参路径不存在: {path}")
        raise AssertionError(f"入参路径不存在: {path}")
    db_value = extract_db_value(result, path)         # 查库值：从查询结果取
```

**解释**（`/data/answer` 走一遍）：
- `column` = `answer`（路径末段，同时是查库取值的列名入参字段名通常与表列名一致）
- `req_value`：从入参 `{"data": {"answer": "c"}}` 取出 `"c"`
- `db_value`：执行器内 `extract_db_value` 从 `{"rows": [{"answer": "c"}]}` 第 1 行取 `answer` 列  `"c"`（列名对不上时：单列取唯一列，多列报错提示 as 别名）

##  预期值 = None  两方校验

```py
    if expected is None:
        if not smart_equal(db_value, req_value):
            msg = f"SQL断言失败: 查库值 {column}={db_value!r} != 入参值 {path}={req_value!r}"
            raise AssertionError(msg)
        return
```

**解释**：适合复杂 JSON 字段整体比对（solution 这种大嵌套结构）直接「库里存的 == 传进去的」。`smart_equal` 做 JSON 归一化：一方是 JSON 字符串一方是 dict/list 时，字符串解析后深度比较，空格/键序差异不算差异。

**关键点**：`!r`（repr）格式化让类型一目了然库是 `'{"ids":["D"]}'`（带引号的 str）、入参是 `{"ids": ["D"]}`（dict），一眼看出差异本质。

##  预期值存在  三方校验

```py
    def sql_op(a, e):
        if op in ('=', '==') and smart_equal(a, e):
            return True
        return OPS[op](a, e)

    try:
        assert sql_op(req_value, expected), f"入参值 {path}={req_value} {op} 期望={expected}"
    except AssertionError:
        log.error(f"SQL断言失败(入参值): {path} 实际={req_value} {op} 期望={expected}")
        raise
    try:
        assert sql_op(db_value, expected), f"查库值 {column}={db_value} {op} 期望={expected}"
    except AssertionError:
        log.error(f"SQL断言失败(查库值): {column} 实际={db_value} {op} 期望={expected}")
        raise
```

**解释**（本例：入参 `"c"`、查库 `"c"`、预期 `"c"`）：
1. **先比入参值**：`"c" == "c"` 过入参错说明请求构造有问题，属最上游
2. **再比查库值**：`"c" == "c"` 过入参对但库里的值不符，正是 SQL 断言要抓的落库 bug

**关键点**：
- 两段结构相同但报错前缀不同（入参值/查库值），pytest 报告一眼定位哪一侧不符
- `sql_op` 只在 `=`/`==` 叠加 smart_equal，`>=` 等数值比较保持原生 OPS 语义

## 收尾：用例结束  平台回调

单条断言失败  AssertionError 上抛  pytest 标记该用例 failed，**下一条用例照常执行**（失败隔离）。全部用例结束后，conftest.py 的 `pytest_terminal_summary` 钩子统计 passed/failed/skipped 并 POST 回调 Django 平台（/update_run_result/）。

## 附：一条断言的完整生命周期（串起来）

以 `set:qid=/question_id; sql:select answer from sp_question_struct where id=${qid}=/data/answer='c'` 为例：

| 步骤 | 发生什么 | 数据形态 |
| --- | --- | --- |
|  | 参数化生成 test_api[case_001] | case = {..., assertions: [...], sql_database: 'exam'} |
|  | 发请求，状态码 200 过 | resp_json = {"question_id": 123} |
|  | 建变量池 | variables = {} |
|  | 第 1 条断言拆前缀 | prefix='set', rest='qid=/question_id' |
|  | assert_set 提取 | variables = {'qid': 123} |
|  | 第 2 条断言拆前缀 | prefix='sql', rest='select ...' |
|  | 变量替换 + 执行 | select answer from sp_question_struct where id=123 |
|  | 拆断言表达式 | path='/data/answer', op='=', expected='c' |
|  | 取两个值 | req_value='c', db_value='c' |
|  | 三方校验 | 入参 'c'='c' 过；查库 'c'='c' 过  用例 PASSED |
| 收尾 | 回调平台 | passed+1 |
