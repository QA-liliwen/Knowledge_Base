# 请求头预组装（build_headers_map）

## 实现内容

`build_headers_map` 把"角色→账号映射 + 账号→token 映射 + 系统头模板"三者合成**全量请求头表**：对每个"已配置角色 × oss/app"组合产出一份完整可用的请求头 dict，键名 `user_{角色}_{端}`。这张表是角色传值链路的中枢——单接口按测试项配置查表取整头，多接口直接嵌入变量池种子。

## 代码来源

`api_app/api_test/api_executor.py`（dispatch_run 上方，L15-27）

---

## 第一部分：函数整体

```py
# 执行准备：一次性组装全量请求头（环境已配置账号的角色 × oss/app）
# 键 = user_{角色}_{端} 
# 值 = 系统对应模板 + 该角色账号对应端的 token + serverId 修正
def build_headers_map(role_user_map, token_map, template_map):
    headers_map = {}
    for role, username in role_user_map.items():
        for system in ('oss', 'app'):
            headers = (template_map.get(system) or {}).copy()
            token = token_map.get(username, {}).get(system, '')
            headers['token'] = token
            # 从 token 末段提取动态 serverId
            server_id = token.split(':')[-1].rstrip('v') if token else ''
            for key in [k for k in headers if k.lower() == 'serverid']:
                headers[key] = server_id
            headers_map[f"user_{role}_{system}"] = headers
    return headers_map
```

**关键点**：

- 纯函数：三个入参三个来源（DB_TestAccount / fetch_tokens 返回值 / DB_HeaderTemplate），无 IO，好测好调。
- 双层循环：外层角色、内层端——产出数量 = `已配置角色数 × 2`；只下发**当前环境已配置账号的角色**（role_user_map 缺的角色不出现在表里）。
- `(template_map.get(system) or {}).copy()`：模板缺失降级空 dict；**必须 copy**，否则下面是原地改模板对象，会污染 template_map（同端下一个角色拿到的就是上一个角色的 token）。

## 第二部分：token 注入

```py
token = token_map.get(username, {}).get(system, '')
headers['token'] = token
```

**关键点**：

- 三级安全取值：账号没登过/该端没取到 → 空串兜底，永远不抛 KeyError。
- 空串 token 也照样下发（头结构完整、值空缺）——执行时该请求自然 401，便于在报告里暴露"这个角色没登上"。
- 同一账号被多个角色映射时，取到的 token 值相同（token 按账号维度获取一次）。

## 第三部分：serverId 动态修正

```py
# 从 token 末段提取动态 serverId
server_id = token.split(':')[-1].rstrip('v') if token else ''
for key in [k for k in headers if k.lower() == 'serverid']:
    headers[key] = server_id
```

**关键点**：

- **token 的真实结构**（冒号分段，实测样例）：
  ```
  462821:1853206711:756ae734-7511-4e38-bbca-045e4d6ae5f6:59e53455...:1201v
   用户id   时间戳        设备/会话uuid                        ...        末段
  ```
  末段 `1201v` = serverId 带尾缀 v；`split(':')[-1]` 取末段 → `rstrip('v')` 去掉尾缀 → `1201`。
- **大小写兼容**：oss 模板里的键是 `serverid`（全小写）、app 模板里是 `serverId`（驼峰），用 `k.lower() == 'serverid'` 不区分大小写匹配，两个键名都命中。
- 为什么必须动态提取：serverId 随账号归属机构/学校变化（实测 org 是 1203、exam 是 1201），硬编码会串号。
- token 为空时不拆（`if token else ''`），serverId 同步落空。

---

## 第四部分：键名规范 user_{角色}_{端}

**关键点**：

- `user_{角色}_{端}` 即 `user_{英文角色值}_{oss|app}`，如 `user_exam_oss`、`user_zhihui_app`。
- 该键名**同时被三方复用**：
  1. 单接口：`build_test_item_cases` 按 `user_{test_item.role}_{test_item.system}` 查表（见 07）；
  2. 多接口：直接作为种子键写进 script_vars.json，脚本用 `{'__var__': 'user_exam_app'}` 引用（见 09/11）；
  3. 日志排查：种子文件/前置信息里一眼对得上角色。
- 之所以"整头下发"而不是"下 token 和 serverId 两个值"：脚本侧引用时零拼装（不用自己记头结构），也避免脚本重写头字段。

## 第五部分：真实产物示例

某次本地执行（run 114）`script_vars.json` 中的实际片段（token 已截断）：

```json
"user_exam_oss": {
  "token": "462821:1853206722:1343bb3e-……（省略）……:1201v",
  "serverid": "1201"
},
"user_exam_app": {
  "DeviceUniqueId": "d91ed0b9-290c-4700-ad1e-1d619d625e54",
  "serverId": "1201",
  "token": "462821:1853206711:756ae734-……（省略）……:1201v"
},
"user_zhihui_oss": {
  "token": "",
  "serverid": ""
}
```

**观察结论**：

- oss 头结构 = `{token, serverid}`，app 头结构 = `{DeviceUniqueId, serverId, token}`（模板字段 + 两个动态值）。
- 全 6 角色 × 2 端 = 12 个键都会出现（只要该环境配了对应角色）；token 为空的键值也完整保留。
- org/student 共用账号的实测：两端 token 值完全相同（"user_org_oss" 与 "user_student_oss" 同值）。

## 整体流程

1. dispatch_run 拿到 role_user_map / token_map / template_map 后调用。
2. 外层遍历角色、内层遍历 oss/app：拷贝模板 → 塞 token → 从 token 末段修正 serverId。
3. 产出 `headers_map {user_{角色}_{端}: 完整头dict}`。
4. 单接口查表取整头塞 case；多接口嵌入 script_vars（common_vars 部分）。
