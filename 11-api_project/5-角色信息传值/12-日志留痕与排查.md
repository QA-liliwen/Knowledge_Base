# 日志留痕与排查（run_header 三通道 + conftest）

## 实现内容

角色传值的可观测性闭环：`run_header_text`（04 组装的四块文案）如何经**三条通道**写入执行日志头部，conftest 如何消费；以及结合用例文件/变量池存档的排查入口。设计原则：角色/账号/token 获取结果的每个环节都留痕，出问题先从日志头部定位。

## 代码来源

- `api_app/api_test/api_executor.py`（run_header_text 组装 L104-122）
- `api_app/api_test/api_local_single_runner.py`（RUN_HEADER 通道）
- `api_app/api_test/api_local_custom_runner.py`（父进程直写通道）
- `api_app/api_test/api_jenkins_single_runner.py` / `api_jenkins_custom_runner.py`（run_header.txt 通道）
- `api_app/api_test/conftest.py`（_dump_run_header）

---

## 第一部分：三条通道对照

| 执行场景 | 传递方式 | 写入时机 | 代码位置 |
| --- | --- | --- | --- |
| 本地单接口 | 环境变量 `RUN_HEADER` | conftest 导入时写 log 头部 | `api_local_single_runner.py` L22 |
| 本地多接口 | **不走环境变量**，父进程直接打开 log 追加写 | Popen 启动前先写 | `api_local_custom_runner.py` L98-109 |
| Jenkins（单/多） | `run_header.txt` 进 zip | Jenkins 构建命令 copy 直写 log 后删除源文件 | `api_jenkins_single_runner.py` / `api_jenkins_custom_runner.py` |

**关键点**：

- **本地多接口为什么不用环境变量**：Windows 下子进程继承的 stdout 句柄无追加语义，pytest 输出会从共享文件指针处**覆盖** conftest 已写入的头部（源码注释明说）——所以父进程先写、`flush` 后再启动 Popen（stdout 指向同一文件），子进程输出顺延其后。
- **Jenkins 为什么塞文件**：环境变量跨机器传递不便，zip 是天然载体；构建命令 copy 写入 log 后 `del` 源文件，保证头部只写一次（避免 conftest 再写一遍）。
- 三条通道最终都落到同一个结果：**log 文件开头是"执行前置信息"，之后才是 pytest 输出**。

## 第二部分：conftest 消费端

```py
# ===== 执行前置信息写入 log（测试项/角色映射/token 结果） =====
# 来源：本地 = 环境变量 RUN_HEADER；Jenkins = 构建命令 copy run_header.txt 直写 log 后删除源文件，
# 此处检测不到即自动跳过（回退兼容：旧配置下仍可从 zip 解压的 run_header.txt 读取)
def _dump_run_header():
    header = os.environ.get("RUN_HEADER")
    if not header:
        header_path = os.path.join(os.path.dirname(os.path.abspath(__file__)), "run_header.txt")
        if os.path.exists(header_path):
            with open(header_path, "r", encoding="utf-8") as f:
                header = f.read()
    if not header:
        return
    log_file_name = os.environ.get("LOG_FILE_NAME")
    if not log_file_name:
        return
    try:
        # 注意：conftest 被 pytest 导入早于 run_request.py 的 sys.path.insert，
        # 此处无法 import log_config，直接拼路径（与 log_config.LOG_DIR 同逻辑）
        log_dir = os.path.join(os.path.dirname(os.path.abspath(__file__)), "..", "data", "logs")
        log_path = os.path.join(log_dir, log_file_name)
        os.makedirs(os.path.dirname(log_path), exist_ok=True)
        with open(log_path, "a", encoding="utf-8") as f:
            f.write(header)
    except Exception as e:
        print(f"[前置信息写入 log 失败] {e}")


_dump_run_header()
```

**关键点**：

- **来源优先级**：环境变量 `RUN_HEADER` → 同目录 `run_header.txt`（回退兼容旧配置）→ 都没有则静默跳过。
- **模块导入时执行**（顶层调用 `_dump_run_header()`）：pytest 收集用例之前头部已写好。
- **路径直拼不能 import log_config**：conftest 被 pytest 导入早于 `run_request.py` 的 `sys.path.insert`（原注释保留）——只能按同逻辑手拼路径。
- 两个变体由 runner 生成时改造（见 10）：本地多接口版 `build_custom_conftest` 把路径替换为**绝对路径** `repr(LOGS_DIR)`；Jenkins 版 `build_jenkins_conftest` 替换为工作区 `logs/`。
- 写失败不炸（try/except + print）——前置信息是辅助手段，不能阻断测试执行。

## 第三部分：日志里能看到什么（排查入口）

log 头部（`run_header_text`，04 组装）四块内容：

```text
==================== 执行前置信息 ====================
执行时间: 2026-09-18 10:30:00
环境: 测试环境 (env_id=2) | 域名: devapi1.lingshi.com | App登录域名: ...
测试项(3):
  [3] 试卷列表 | 角色: exam | 测试端: app
  ...
角色映射(环境 测试环境，共6条):
  exam -> adminexam
  org -> adminqwqwqw
  ...
token 获取结果:
  adminexam: oss=462821:1853...:1201v | app=462821:1853...:1201v
  adminvswrr: oss=(失败/空) | app=(失败/空)
======================================================
```

**关键点**：

- 四块定位法：
  1. 环境行 → 确认执行目标（域名/环境段/app_server）；
  2. 测试项清单 → 确认本次跑了哪些项、各自的**角色/端**配置；
  3. 角色映射表 → 确认该环境配了哪些 `role -> user`；
  4. token 结果 → **"某角色 401"排查第一站**：哪个账号、哪个端没登上，直接显示 `(失败/空)` 占位符。
- 配合其他落盘：
  - 单接口：`single_cases/{run_id}_cases.txt`（用例里 headers 是**执行时实际整头**）+ `report_{run_id}.xml`；
  - 多接口：执行现场 `custom_runs/{run_id}/script_vars.json` + 平台存档 `custom_var/{run_id}_var.json`（脚本拿到的**变量原文**）；
  - Jenkins：构建命令把 run_header 写入同一 log，pytest 输出重定向追加（见 `data/Jenkins配置.md`）。

## 第四部分：典型排查路径

| 现象 | 排查动作 |
| --- | --- |
| 某角色请求 401 | 看 log 头部 token 结果 → 该角色对应账号 token 为空 → 查登录：FIXED_PASSWORDS 是否命中、临时密码申请是否报错（05 篇三级策略） |
| 脚本变量没替换（URL 残留占位） | 查 `script_vars.json` / `custom_var` 存档里是否有该键；核对种子键与脚本名是否 `test_flow_{id}.py` 对齐（09/11） |
| serverId 串号 | 看种子里的 `serverid`/`serverId` 是否与 token 末段一致（06 动态提取逻辑） |
| 请求头整个没带上 | 检查测试项 `role`/`system` 是否为空 → `user_` 查表降级空头（07） |
| 头部没写进 log | 对照三条通道：本地单接口看 `RUN_HEADER`、本地多接口看父进程直写、Jenkins 看构建命令是否 copy；conftest 写失败会 print `[前置信息写入 log 失败]` |

**关键点**：

- 排查顺序建议：**log 头部（谁/什么环境/什么角色）→ 用例或变量存档（实际下发值）→ 报告（哪条挂了）**——三层信息互相印证。

---

## 整体流程

1. dispatch_run 组装 `run_header_text`（环境/测试项/角色映射/token 结果，04）。
2. 按通道落地：本地单接口 → 环境变量；本地多接口 → 父进程直写；Jenkins → `run_header.txt` 进 zip 由构建命令直写。
3. conftest 导入时 `_dump_run_header` 把头部写入 log 开头；pytest 输出随后顺延/追加。
4. 终态 `pytest_terminal_summary` 统计结果并回调平台（含 Jenkins 构建链接与报告文件名）。
5. 排查时按"log 头部 → 种子/用例存档 → 报告"逐层定位。
