# 角色信息传值 · 代码核心链路

## 实现内容

本模块覆盖"角色"这一数据从**前端配置**到**脚本消费**的完整链路。核心设计：角色值统一存英文（zhihui/exam/content/org/student/afterschool），执行时按"环境×角色"解析账号、批量获取 token、一次预组装请求头（键名 `user_{角色}_{端}`），最终通过两条通道（单接口 cases 对象 / 多接口 script_vars.json）送达测试代码，并把角色映射与 token 结果写入执行日志头部留痕。

## 数据流全景

```
[配置侧]
前端 RunList.vue「角色配置」弹窗（环境×角色→账号）
    ↓ POST /update_test_accounts/（全量覆盖）
DB_TestAccount（env + role → username，唯一约束 env+role）

前端 TestItemList.vue 测试项编辑（单接口用例）
    ↓ POST /update_test_item/
DB_TestItem.role / system（测试项绑定角色与测试端）

[执行侧] 前端 POST /execute_run/ → dispatch_run
    env_id → 全量查 DB_TestAccount → role_user_map {角色: 账号}
        ↓ 用户名去重
    fetch_tokens（token_fetcher）→ {账号: {oss: token, app: token}}
        ↓
    build_headers_map → headers_map { user_{角色}_{端}: 完整请求头 dict }
        ↓
        ├── 单接口（type1）：build_test_item_cases 按测试项 role/system 查表
        │       → {run_id}_cases.txt → 本地 pytest / Jenkins 打包
        │       → run_request.py 直接使用 headers 发请求
        ├── 多接口（type2）：script_vars = domain/env + headers_map + inputs
        │       → script_vars.json（本地 custom_runs/{run_id}/ 或 Jenkins zip）
        │       → 脚本 resolve_refs 解析 {'__var__'} 占位消费
        └── 前置信息 run_header_text（角色映射 + token 结果）
                → 写入执行日志头部（本地父进程直写 / Jenkins copy 直写）
```

## 贯穿全链路的设计决策

1. **英文贯穿**：数据库存储、请求头键名、脚本变量统一使用英文角色值；中文只在展示层由 role_labels.js 映射。中文无法可靠地嵌进请求头键名与 Python 变量名。
2. **执行时全量取数**：不按测试项逐个取 token，而是按当前环境一次性解析全部角色账号；用户名去重后批量获取；任一账号 token 失败不拦截，落空串（用例自然 401，报告可见）。
3. **一次预组装、两条通道复用**：headers_map 同时服务单接口（查表塞进 case）与多接口（嵌入变量池种子），是整条链路的中枢。
4. **优先级契约**：多接口入参 inputs 在种子中最后合并，覆盖平台注入的同名键；脚本侧 `{'__var__'}` 未命中时保留占位原样。
5. **可观测性**：角色映射表与 token 获取结果写入每次执行的日志头部（前置信息），排查"哪个角色没登上"第一步就看这里。

## 整条链路一句话版本

前端配置"环境×角色→账号"与"测试项→角色+端" → 执行时按环境全量解析角色账号、批量取 token → 预组装 `user_{角色}_{端}` 请求头 → 单接口查表塞 case、多接口作种子写 file → 脚本侧引用即用 → 全过程留痕日志头部。
