# 单接口执行与消费（两条通道 + run_request）

## 实现内容

dispatch_run 的 type1 分支（L124-172）把组装好的用例落盘后分派执行：本地走 `run_single_local`（子进程 pytest）、Jenkins 走 `pack_test_bundle` + 触发构建。执行端 `run_request.py` 用 pytest 参数化消费用例文件，headers 原样使用、零解析。

- `api_app/api_test/api_executor.py`（type1 分支 L124-172）

- `api_app/api_test/api_jenkins_single_runner.py`（pack_test_bundle）
- `api_app/api_test/run_request.py`（消费部分 L254-290）

## 第二部分：本地通道 run_single_local

```py
# 启动 pytest 子进程
def run_single_local(test_run, cases_txt_path, sql_conn=None, run_header=""):
    started_ts = time.time()

    # 日志文件
    log_file_name = f"{test_run.id}_app.log"
    test_run.log_file = log_file_name
    test_run.save()

    # 启动 pytest 子进程
    pytest_env = os.environ.copy()
    pytest_env["TEST_RUN_ID"] = str(test_run.id)
    pytest_env["LOG_FILE_NAME"] = log_file_name
    pytest_env['STARTED_AT'] = str(started_ts)
    pytest_env["RUN_HEADER"] = run_header  # 执行前置信息（conftest 启动时写入 log 头部）
    # SQL 断言连接四要素（未配置则不注入，sql: 断言自动跳过）
    if sql_conn:
        for key, value in sql_conn.items():
            pytest_env[key] = value
    subprocess.Popen(
        ["pytest", os.path.join(BASE_DIR, "run_request.py"), "-v", f"--cases-file={cases_txt_path}"],
        env=pytest_env,
        cwd=BASE_DIR,
    )
```

**关键点**：

- **环境变量传参**是本地单接口通道的全部上下文：`TEST_RUN_ID`（回调）、`LOG_FILE_NAME`（日志名）、`STARTED_AT`（耗时）、`RUN_HEADER`（角色传值前置信息）、SQL 四要素（按需）。
- **角色传值走 `RUN_HEADER`**：`run_header_text`（04 组装）经环境变量注入 → conftest 启动时写入 log 头部（三条通道见 12）。单接口**没有**变量池种子——头的注入发生在 07 组装阶段，已完成。
- `subprocess.Popen` 不等待：dispatch_run 立即返回、前端轮询状态；终态回调由 `conftest.pytest_terminal_summary` 完成。
- `cwd=BASE_DIR` 直接跑平台源码目录里的 `run_request.py`（单接口不需要目录隔离，与多接口的 custom_runs 机制不同）。

## 第三部分：Jenkins 通道

```py
        # 执行用例
        if run_mode == 'jenkins':
            zip_bytes = pack_test_bundle(test_run, cases_txt_path, run_header_text)
            try:
                jenkins_url = trigger_jenkins_build(zip_bytes, test_run.id, base_url, sql_conn)

            test_run.jenkins_build_url = jenkins_url
            test_run.log_file = f"{test_run.id}_app.log"  # 日志文件名（与 Jenkins batch 的 LOG_FILE_NAME 一致），供前端拼日志链接
            test_run.save()
            results.append({"type": 1, "run_id": test_run.id, "jenkins_build_url": jenkins_url})
        else:
            run_single_local(test_run, cases_txt_path, sql_conn, run_header_text)
            results.append({"type": 1, "run_id": test_run.id})
```

**关键点**：

- `pack_test_bundle` 把 conftest / run_request / sql_assert / log_config / requirements / 用例文件 / `run_header.txt` / `pytest.ini` 打包成 zip。
- **角色传值在 Jenkins 通道走 `run_header.txt` 文件**（zip 内），不设环境变量——构建命令 copy 直写 log 后删除源文件（见 12）。
- `pytest.ini` 两个关键配置：`addopts = --cases-file={用例文件名}`（执行入参固化）+ `python_files = run_request.py test_*.py`（`run_request.py` 不符合 pytest 默认收集规则，必须显式加入）。
- 触发失败：`test_run` 置 failed 并返回 500；成功后回填 `jenkins_build_url`（前端跳构建页）与 `log_file`（前端拼日志链接，文件名与 Jenkins batch 的 `LOG_FILE_NAME` 对齐）。
- 本地/Jenkins 两条通道对 dispatch_run 的返回结构不同：本地只回 `run_id`（无构建链接），Jenkins 回 `jenkins_build_url`。

## 第四部分：执行端消费（run_request.py）

**pytest 参数化入口**：

```py
# ===== pytest 入口 =====
def pytest_generate_tests(metafunc):
    cases_file = metafunc.config.getoption("--cases-file") or os.environ.get("CASES_FILE")
    if not cases_file:
        return
    with open(cases_file, "r", encoding="utf-8") as f:
        cases_data = json.load(f)

    metafunc.parametrize(
        "case",
        cases_data,
        ids=[c['CaseID'] for c in cases_data]
    )


def test_api(case):
    run_main(case)
```

**执行层**：

```py
# 执行层
def run_request(url, method, headers, body=None):
    log.info(f"准备发送请求: {method.upper()} {url}")
    log.debug(f"请求头: {headers}")
    log.debug(f"请求体: {body}")
    if method == 'GET':
        if body:
            url = url + '?' + str(body)
        return requests.get(url, headers=headers)
    elif method == 'POST':
        return requests.post(url, headers=headers, json=body)
    else:
        return requests.request(method, url, headers=headers, json=body)
```

**run_main 中的调用点**：

```py
    resp = run_request(url=case['url'], method=case['method'], headers=case['headers'], body=case.get('body', ''))
```

**关键点**：

- 参数化：一条用例 = 一个 test item，`ids=CaseID`——测试报告里的用例名就是 CaseID。
- **headers 原样使用、执行端零解析**：组装的用例文件里 headers 已是定稿整头（含 token），执行端对"角色"概念完全无感知——角色传值的复杂度全部收敛在 dispatch_run 准备阶段。
- `is_active != 'Y'` → `pytest.skip`（用例级开关）。
- 每条用例独立变量池：`set:` 提取变量供同用例后续 `sql:` 引用；断言分发（len/exists/type/header/in 内置 + 表达式断言 + SQL 断言）。
- 终态回调：conftest 的 `pytest_terminal_summary` 统计 passed/failed/skipped 后 POST 平台（见 12）。

## 整体流程

1. type1 分支：查 SQL 配置 → 建 `DB_run_result` → `build_test_item_cases` 组装 → 写 `{run_id}_cases.txt`。
2. 按 `run_mode` 分派：本地 → `run_single_local`（Popen pytest，`RUN_HEADER` 环境变量）；Jenkins → `pack_test_bundle` + `trigger_jenkins_build`（`run_header.txt` 进 zip）。
3. pytest 参数化读用例文件 → `run_main` → `run_request` 发请求（headers 原样）。
4. 终态 conftest 回调平台，前端展示结果/日志/报告。
