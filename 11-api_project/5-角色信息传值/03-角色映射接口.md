# 角色映射接口（views_test_item.py）

## 实现内容

后端接口层负责角色信息的读写：`get_test_accounts` 一次返回"角色清单 + 全量账号映射"供前端两个场景共用；`update_test_accounts` 以全量覆盖方式保存映射；测试项的 detail/update 接口读写 `role/system/script_inputs` 字段；`execute_run` 是执行链路的统一入口。

## 代码来源

- `api_app/views_test_item.py`
- `api_project/urls.py`

## 第一部分：读取角色映射 get_test_accounts

```py
# 角色映射（环境×角色→账号；roles 供测试项编辑与配置弹窗共用）
def get_test_accounts(request):
    accounts = list(DB_TestAccount.objects.filter(is_del=False).values('env_id', 'role', 'username'))
    return JsonResponse({"roles": TEST_ROLES, "accounts": accounts})
```

**关键点**：

- 一次请求返回两样东西：`roles`（英文角色清单，来自 models 常量）+ `accounts`（扁平数组，每项 `{env_id, role, username}`）。
- 前端**三个场景共用**这一个接口：测试项编辑的角色单选组（只用 roles）、角色配置弹窗（roles + accounts 回填）、测试项列表渲染。
- `accounts` 返回扁平数组而非嵌套字典，前端自己按 `env_id + role` 组矩阵。
- 返回的字段名是 `env_id`，与前端矩阵初始化时的 `matrix[e.id]` 对应。

## 第二部分：保存角色映射 update_test_accounts

```py
# 保存角色映射（全量覆盖：空用户名的格子不落库）
def update_test_accounts(request):
    if request.method != 'POST':
        return JsonResponse({"code": -1, "message": "仅支持 POST 请求"}, status=405)
    data = json.loads(request.body)
    accounts = data.get('accounts', [])

    DB_TestAccount.objects.all().delete()
    objs = [
        DB_TestAccount(env_id=a.get('env_id'), role=a.get('role', ''), username=a.get('username', ''))
        for a in accounts if a.get('env_id') and a.get('role') and a.get('username')
    ]
    DB_TestAccount.objects.bulk_create(objs)
    return JsonResponse({"code": 0, "message": "保存成功", "count": len(objs)})
```

**关键点**：

- **全删全建**：先 `delete()` 清空整表，再 `bulk_create` 重建。前端每次提交 18 格全量数据，后端不需要做增删改 diff，逻辑最简。
- 过滤条件：`env_id`、`role`、`username` 三者缺一不落库——对应"空格子不保存"。
- 是**物理删除**（不是软删 is_del），因为提交即权威快照，没有增量状态需要保留。
- 返回 `count`（实际落库条数），前端保存成功提示直接显示。
- 注意：全删全建没有事务包裹，理论上有并发写入风险；实际是单人操作的低频配置接口，未做处理（与"系统不需要过度严谨"的取舍一致）。

## 第三部分：测试项中的角色字段读写

**详情接口（编辑回填）**：

```py
def get_test_item_detail(request):
    item = DB_TestItem.objects.filter(id=item_id, is_del=False).first()
    ...
    return JsonResponse({
        "code": 0,
        "data": {
            ...
            "role": item.role,
            "system": item.system,
            ...
        }
    })
```

**保存接口（角色相关行）**：

```py
def update_test_item(request):
    ...
    item.script_inputs = data.get('script_inputs', item.script_inputs if not is_create else '')
    item.role = data.get('role', item.role if not is_create else '')
    item.system = data.get('system', item.system if not is_create else '')
    ...
    item.save()
```

**关键点**：

- 读写模式统一：`data.get('字段', 原值)`——**不传字段 = 保持原值**，传空串 = 清空。前端 type=2 保存时显式传 `''`，所以多接口脚本测试项的 role/system 会被清空。
- 接口**不校验** role 值是否在 TEST_ROLES 里（前端单选组已保证取值范围；后端不做强校验，与整体"前端拦截为主"的取舍一致）。
- `script_inputs`（多接口入参 JSON 文本）同段落处理，前端已校验 JSON 合法性。

## 第四部分：执行入口 execute_run

```py
def execute_run(request):
    if request.method != 'POST':
        return JsonResponse({"code": -1, "message": "仅支持 POST 请求"}, status=405)
    if not request.body:
        return JsonResponse({"code": -1, "message": "请求体为空"}, status=400)
    try:
        data = json.loads(request.body)
    except json.JSONDecodeError:
        return JsonResponse({"code": -1, "message": "请求体不是合法 JSON"}, status=400)

    result, status_code = dispatch_run(data)
    return JsonResponse(result, status=status_code)
```

**关键点**：

- 只做协议层校验（方法/非空/合法 JSON），业务逻辑全部下探 `dispatch_run`（见 04）。
- 前端提交体含 `test_item_ids / domain_id / env_id / description / run_mode`，其中 `env_id` 就是角色解析的查询条件。

## 第五部分：路由

```py
path('get_test_accounts/', get_test_accounts),  # 获取角色映射（环境×角色→账号）
path('update_test_accounts/', update_test_accounts),  # 保存角色映射（全量覆盖）
path('execute_run/', execute_run),  # 执行测试（本地/Jenkins，由 run_mode 区分）
path('get_test_item_detail/', get_test_item_detail),  # 获取测试项详情（编辑回填）
path('update_test_item/', update_test_item),  # 更新测试项
```

**关键点**：

- 角色相关就两对读写接口：映射（get/update_test_accounts）+ 测试项（detail/update_test_item）。
- 路由无鉴权中间件（内网团队工具）。

---

## 整体流程

1. 前端进页面/开弹窗 → `get_test_accounts` → 拿到 roles（渲染）+ accounts（回填）。
2. 保存配置 → `update_test_accounts` → 全删全建 DB_TestAccount。
3. 测试项编辑 → `get_test_item_detail` 回填 role/system → 保存走 `update_test_item`。
4. 执行 → `execute_run` 透传参数给 `dispatch_run`，角色解析从 `env_id` 开始。
