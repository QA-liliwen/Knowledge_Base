# 多接口通道落地（本地目录 / Jenkins 打包 / 存档）

## 实现内容

`script_vars` 种子组装完成后（09），由两条通道落地到执行现场：本地 `run_custom` 写 `custom_runs/{run_id}/` 执行目录；Jenkins `pack_custom_bundle` 打进 zip。无论哪条通道，dispatch_run 最后都把种子存档到 `custom_var/{run_id}_var.json` 留痕。

## 代码来源

- `api_app/api_test/api_local_custom_runner.py`（run_custom）
- `api_app/api_test/api_jenkins_custom_runner.py`（pack_custom_bundle）
- `api_app/api_test/api_executor.py`（type2 分派 + 存档 L190-205）

## 第一部分：本地通道 run_custom

```py
    # 创建本次执行的临时目录（放在 data 目录下，上级目录无 conftest.py，不会加载父目录 conftest）
    run_dir = os.path.join(CUSTOM_RUNS_DIR, str(test_run.id))
    os.makedirs(run_dir, exist_ok=True)

    # 将每个测试项的脚本文件复制到执行目录
    try:
        for item_id in test_item_ids:
            test_item = DB_TestItem.objects.get(id=item_id)
            if not test_item.script_filename:
                raise ValueError(f"测试项 {item_id} 未上传脚本文件")
            src_path = os.path.join(SCRIPTS_DIR, test_item.script_filename)
            if not os.path.exists(src_path):
                raise FileNotFoundError(f"脚本文件不存在: {test_item.script_filename}")
            dst_name = f"test_flow_{item_id}.py"
            dst_path = os.path.join(run_dir, dst_name)
            with open(src_path, "r", encoding="utf-8") as f:
                content = f.read()
            with open(dst_path, "w", encoding="utf-8") as f:
                f.write(content)
    except Exception as e:
        test_run.status = "failed"
        test_run.save()
        return {"code": -1, "message": str(e)}, 400

    # 写入脚本运行数据（变量池种子：domain/env + 全量头 user_{角色}_{端} + 各脚本入参）
    if script_vars:
        with open(os.path.join(run_dir, "script_vars.json"), "w", encoding="utf-8") as f:
            json.dump(script_vars, f, ensure_ascii=False, indent=2)
```

**关键点**：

- 每次执行按 run_id 新建目录 `data/custom_runs/{run_id}/`：脚本副本（`test_flow_{id}.py`）+ `script_vars.json` + `conftest.py` + 报告 XML。执行现场彼此隔离、可复查。
- 脚本**重命名机制**：源文件按 `script_filename` 存放（`data/custom_scripts/`），复制时统一改名 `test_flow_{item_id}.py`——与 09 的种子键对齐，脚本引用自己的索引。
- `script_vars.json` 与脚本**同目录**——脚本用 `os.path.dirname(__file__)/script_vars.json` 直接读（见 11），无需任何路径参数。
- 脚本缺失/未上传 → 400 直接拦截（脚本是硬依赖，与"token 失败不拦截"的取舍不同）。
- 目录位置注释有讲究：custom_runs 的**上级目录不能有 conftest.py**（pytest 会沿目录树上溯加载），data 目录天然安全。

**conftest 与日志头部（本地多接口专属处理）**：

```py
    # 写入 conftest.py（用于跑完后回调平台；日志目录改为绝对路径，指向平台统一 logs 目录）
    with open(os.path.join(run_dir, "conftest.py"), "w", encoding="utf-8") as f:
        f.write(build_custom_conftest())
    ...
    # 注意：前置信息不走 RUN_HEADER 环境变量——Windows 下子进程继承的 stdout 句柄无追加语义，
    # pytest 输出会从共享文件指针处覆盖 conftest 追加写的头部，故由父进程直接先写入 log
    ...
    log_file = open(os.path.join(LOGS_DIR, log_file_name), "a", encoding="utf-8")
    if run_header:
        log_file.write(run_header)
        log_file.flush()
    subprocess.Popen(
        ["pytest", run_dir, "-v", f"--junitxml={os.path.join(run_dir, report_file)}"],
        env=pytest_env,
        cwd=run_dir,
        stdout=log_file,
        stderr=subprocess.STDOUT,
    )
    log_file.close()
```

**关键点**：

- `build_custom_conftest`：读平台 conftest 源码，把日志目录的相对路径替换为**绝对路径**（`repr(LOGS_DIR)`）——因为执行目录在 `custom_runs/` 下，原相对路径 `../data/logs` 会解析错位置（三条 run_header 通道汇总见 12）。
- **角色传值前置信息由父进程直接先写 log**：打开日志文件追加写 `run_header` → flush → 再启动 Popen（stdout 指向同一文件句柄，输出顺延其后）——这是"Windows 子进程 stdout 无追加语义"的绕行方案。
- pytest 直接以目录为参数运行（`pytest run_dir`），脚本命名 `test_flow_*.py` 符合默认收集规则，无需 `--cases-file`。
- 报告：`--junitxml={run_id}/report_{run_id}.xml` 落执行目录，回调时上报文件名。

## 第二部分：Jenkins 通道 pack_custom_bundle

```py
    # 打包 zip
    buf = io.BytesIO()
    with zipfile.ZipFile(buf, 'w', zipfile.ZIP_DEFLATED) as zf:
        zf.writestr("conftest.py", conftest_content)
        zf.writestr("log_config.py", build_jenkins_log_config())
        zf.writestr("requirements.txt", "requests\npytest\npytest-html\n")
        for name, content in scripts.items():
            zf.writestr(name, content)
        # 脚本运行数据（变量池种子：domain/env + 全量头 user_{角色}_{端} + 各脚本入参）
        if script_vars:
            zf.writestr("script_vars.json", json.dumps(script_vars, ensure_ascii=False, indent=2))
        # 执行前置信息（conftest 启动时写入 log 头部；pytest 输出由 Jenkins 构建命令重定向追加进同一 log，见 data/Jenkins配置.md）
        zf.writestr("run_header.txt", run_header)
```

**关键点**：

- zip 内容：`conftest.py` + `log_config.py` + `requirements.txt` + 各 `test_flow_{id}.py`（key 即最终文件名，读源码时就以 `test_flow_{item_id}.py` 为键）+ `script_vars.json` + `run_header.txt`。
- **`script_vars.json` 以字符串写入 zip**：Jenkins 解压后与脚本同目录，脚本读取方式与本地通道**完全一致**——种子契约（文件名 + 索引键 + 同目录位置）跨通道统一，脚本零感知。
- `run_header.txt` 进 zip：Jenkins 构建命令 copy 直写 log 后删除源文件；与本地通道的"父进程直写"不同（见 12）。
- 无 `pytest.ini`：多接口脚本本身是 `test_*.py` 命名，无需显式收集规则（单接口通道才需要）。
- `conftest.py`/`log_config.py` 均由 `build_jenkins_*` 改造：日志目录改为工作区 `logs/` 相对路径。

## 第三部分：dispatch_run 的分派与存档

```py
        if run_mode == 'jenkins':
            resp, status = run_custom_jenkins(type2_ids, description, base_url, env=env_name, script_vars=script_vars, run_header=run_header_text)
        else:
            resp, status = run_custom(type2_ids, description, base_url, env=env_name, script_vars=script_vars, run_header=run_header_text)
        if status != 200:
            return resp, status
        # 变量字典存档到固定目录（重要比对数据，与 single_cases 下的用例文件对应）
        run_id = resp.get("run_id")
        var_dir = os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "data", "custom_var")
        with open(os.path.join(var_dir, f"{run_id}_var.json"), "w", encoding="utf-8") as f:
            json.dump(script_vars, f, ensure_ascii=False, indent=2)
        results.append({
            "type": 2,
            "run_id": run_id,
            "jenkins_build_url": resp.get("jenkins_build_url", ""),
        })
```

**关键点**：

- 两条通道调用**签名一致**（test_item_ids, description, base_url, env, script_vars, run_header）——分派只差函数名，差异全部封装在 runner 内部。
- 非 200 直接透传 `(resp, status)`（如脚本缺失的 400、Jenkins 触发失败的 500）。
- **存档 `custom_var/{run_id}_var.json`**：执行现场（custom_runs 目录或 Jenkins 工作区）会被清理，平台侧留一份**种子原文**永久可查——排查"脚本实际拿到的变量是什么"以它为准。
- 存档内容含 token（明文），与 `single_cases/{run_id}_cases.txt` 的用例文件（含整头）相对应：单接口看 cases 文件、多接口看 var 文件。
- `run_custom`/`run_custom_jenkins` 内部各自建 `DB_run_result`（trigger_source 分别为 local/jenkins），并返回 `run_id` + 构建链接（本地无链接）。

## 整体流程

1. dispatch_run type2 分派：本地 → `run_custom`；Jenkins → `run_custom_jenkins`（入参一致）。
2. 本地：`custom_runs/{run_id}/` 放脚本副本 + 种子 + conftest → 父进程先写日志头 → Popen pytest（stdout 直落共享日志）。
3. Jenkins：zip 打包（含种子 + `run_header.txt`）→ 触发构建 → Jenkins 端解压执行（脚本读种子方式一致）。
4. 返回 `run_id`；dispatch_run 把种子另存 `custom_var/{run_id}_var.json`。
5. 执行终态 conftest 回调平台（见 12）。
